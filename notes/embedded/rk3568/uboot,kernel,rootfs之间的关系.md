本文档概述了嵌入式Linux系统启动过程中的关键组件：U-Boot、U-Boot SPL、Linux内核、设备树（DTS）和根文件系统（Rootfs）。每个组件在系统初始化和运行中都扮演着重要角色。

## 1. U-Boot
### 概述
U-Boot，全称为Universal Boot Loader，是嵌入式系统中广泛使用的引导加载程序（Bootloader）。其作用类似于Windows中的BIOS，负责硬件初始化和加载操作系统。

### 功能
+ **硬件初始化**：配置DDR内存、时钟等关键外设。
+ **内核加载**：从存储设备（例如QSPI Flash、SD卡、eMMC）或网络加载Linux内核到板载DDR内存中执行。
+ **启动流程**：加载必要的镜像和参数后，将控制权移交内核。

### 与其他引导加载程序的比较
其他引导加载程序如Vivi和RedBoot也存在，但U-Boot因其灵活性和广泛的硬件支持而最为流行。

### 角色
U-Boot的主要目的是准备系统并启动内核。一旦内核启动，U-Boot的任务即告结束。

## 2. U-Boot SPL（二级程序加载器）
### 概述
U-Boot SPL（Secondary Program Loader）是某些嵌入式系统中用于加载完整U-Boot引导程序的轻量级程序。并非所有系统都明确使用SPL，它可能集成在芯片的BootROM中。

### 功能
+ **预初始化**：初始化外部RAM（例如DDR），因为完整的U-Boot镜像（几百KB）通常超出片上RAM的容量。
+ **加载U-Boot**：从存储设备加载并启动完整的U-Boot镜像。
+ **二级引导**：相对于芯片的BootROM（上电后首先执行的固化程序），SPL是二级引导程序。

### 实现
SPL通常由U-Boot源代码提供，针对特定硬件定制，其小巧的体积适合片上内存限制。

### 角色
SPL在芯片BootROM和完整U-Boot之间起到桥梁作用，使系统能够加载更大的引导程序。

## 3. Linux内核
### 概述
Linux内核是开源的操作系统内核，管理硬件资源并为用户应用程序提供运行平台。在嵌入式系统中，它常与FreeRTOS、uC/OS等轻量级操作系统并存。

### 功能
+ **硬件管理**：通过驱动程序初始化和管理硬件。
+ **驱动开发**：嵌入式Linux开发主要集中在驱动移植，通常基于芯片厂商提供的内核。
+ **基于框架的开发**：驱动开发需遵循Linux内核规定的标准化框架。

### 开发流程
开发人员通常不会从纯净内核开始，而是基于厂商提供的内核，适配特定开发板的外设和硬件配置。

### 角色
内核是操作系统的核心，充当硬件与用户空间应用程序之间的接口。

## 4. 设备树（DTS）
### 概述
设备树（Device Tree，DTS）是一种用于描述开发板硬件配置的数据结构。它是为了应对System-on-Chip（SoC）支持的复杂性而引入的。

### 功能
+ **硬件描述**：定义开发板的设备、外设及其配置。
+ **模块化**：允许硬件细节在内核外部指定，减少内核代码臃肿。
+ **历史背景**：设备树最初在PowerPC等架构中使用，后成为Linux支持多样化SoC的标准。

### 角色
设备树使内核能够动态适应不同硬件配置，而无需重新编译。

## 5. 根文件系统（Rootfs）
### 概述
根文件系统（Rootfs）是内核启动后挂载的第一个文件系统，包含用户空间环境，包括库、工具和应用程序，是系统正常运行的基础。

### 功能
+ **系统初始化**：托管初始用户空间进程（例如`/sbin/init`或`systemd`）。
+ **核心组件**：包括`/bin`、`/etc`、`/lib`等目录，以及BusyBox等工具。
+ **依赖性**：内核需要根文件系统才能正常工作；没有Rootfs，系统无法运行。

### 创建工具
+ **BusyBox**：轻量级工具集，适合手动构建最小化根文件系统。
+ **Buildroot**：包含BusyBox功能，简化根文件系统生成。
+ **Yocto**：强大的框架，用于生成定制化的根文件系统。

### 开发方式
+ 快速构建：使用Buildroot生成根文件系统。
+ 深入学习：使用BusyBox手动构建根文件系统以了解过程。

### 角色
根文件系统提供用户空间环境，支持应用程序和服务运行。

## 组件之间的关系
+ **启动顺序**：
    1. **BootROM**：上电后执行，加载U-Boot SPL（如果存在）。
    2. **U-Boot SPL**：初始化外部RAM并加载完整U-Boot。
    3. **U-Boot**：加载内核、设备树并传递启动参数。
    4. **内核**：初始化硬件，挂载根文件系统，启动用户空间初始化进程。
    5. **根文件系统**：提供用户空间环境，完成系统运行。
+ **依赖关系**：
    - U-Boot（及SPL）为内核启动做准备。
    - 内核依赖设备树进行硬件配置，依赖根文件系统提供用户空间功能。
    - 根文件系统依赖内核挂载并运行。

### 小结
+ **U-Boot**：初始化硬件并加载内核。
+ **U-Boot SPL**：协助加载完整U-Boot，解决片上内存限制。
+ **Linux内核**：管理硬件并提供用户空间接口。
+ **设备树（DTS）**：描述硬件配置，增强内核灵活性。
+ **根文件系统（Rootfs）**：提供用户空间环境，完成系统功能。

通过这些组件的协作，嵌入式Linux系统能够从上电到运行完整操作系统，满足多样化的应用需求。

## <font style="color:rgb(0, 0, 0);">Linux启动过程</font>
<font style="color:rgb(0, 0, 0);">正常启动过程中，Bootloader首先运行，然后将内核复制到内存中（或者在固态存储设备上直接运行，但是效率较低），并在内存某个固定的地址（包括地址与参数的结构）设置好要传递给内核的参数，最后运行内核。内核启动后，挂载（mount）根文件系统（Root filesystem），启动文件系统中的应用程序。</font>

<font style="color:rgb(0, 0, 0);">上电 ——> Bootloader —[传递参数]—> 加载内核 ——> 内核挂载根文件系统 ——>执行应用程序</font>

## <font style="color:rgb(0, 0, 0);">如何理解Bootloader与Kernel</font>
<font style="color:rgb(0, 0, 0);">操作系统内核本身就是一个裸机程序，和我们学的uboot和其他裸机程序没有本质的区别；事实上，不少U-Boot源码就是根据相应的Linux内核源程序进行简化而形成的，尤其是一些设备的驱动程序。如果我们去琢磨U-Boot源码的注释，便会轻易的发现这一情况。</font>

<font style="color:rgb(0, 0, 0);">区别就是操作系统运行起来后可以分为应用层（用户态）和内核层（内核态），分层后，两层的权限不同（实现的原理是基于CPU的模式切换），内存访问和设备操作的管理上更加精细（内核可以随便方位各种硬件，而应用程序只能被限制的访问硬件和内存地址）。</font>

<font style="color:rgb(51, 51, 51);">以ARM处理器为例，除用户模式外，其余6种工作模式都属于特权模式：</font>

<font style="color:rgb(51, 51, 51);">用户模式（USR）：正常程序执行模式，不能直接切换到其他模式  
</font><font style="color:rgb(51, 51, 51);">系统模式（SYS）：运行操作系统的特权任务，与用户模式类似，但具有可以直接切换到其他模式等特权  
</font><font style="color:rgb(51, 51, 51);">快中断模式（FIQ）：支持高速数据传输及通道处理，FIQ异常响应时进入此模式  
</font><font style="color:rgb(51, 51, 51);">中断模式（IRQ）：用于通用中断处理，IRQ异常响应时进入此模式  
</font><font style="color:rgb(51, 51, 51);">管理模式（SVC）：操作系统保护模式，系统复位和软件中断响应时进入此模式（由系统调用执行软中断SWI命令触发）  
</font><font style="color:rgb(51, 51, 51);">中止模式（ABT）：用于支持虚拟内存和/或存储器保护，在ARM7TDMI没有大用处  
</font><font style="color:rgb(51, 51, 51);">未定义模式（UND）：支持硬件协处理器的软件仿真，未定义指令异常响应时进入此模式</font>

<font style="color:rgb(0, 0, 0);">Linux内核态是从ARM的SVC即管理模式下启动的，但在某些情况下、如：硬件中断、程序异常（被动）等情况下进入ARM的其他特权模式，这时仍然可以进入内核态（因为就是可以操作内核了）；同样，Linux用户态是从ARM用户模式启动的，但当进入ARM系统模式时、仍然可以操作Linux用户态程序（进入用户态，如init进程的启动过程）。  
</font><font style="color:rgb(0, 0, 0);">即：Linux内核从ARM的SVC模式下启动，但内核态不仅仅指ARM的SVC模式（还包括可以访问内核空间的所有ARM模式）；Linux用户程序从ARM的用户模式启动，但用户态不仅仅指ARM的用户模式。</font>

<font style="color:rgb(0, 0, 0);">直观来看：uboot的镜像是u-boot.bin，Linux系统的镜像是zImage（也可以是uImage，关系不大），这两个东西其实都是裸机程序镜像。从系统启动的角度来讲，内核和uboot都是裸机程序。</font>

## <font style="color:rgb(0, 0, 0);">文件系统</font>
### <font style="color:rgb(0, 0, 0);">概念</font>
<font style="color:rgb(0, 0, 0);">Linux文件系统中的文件是数据的集合，文件系统不仅包含着文件中的数据而且还有文件系统的结构，所有Linux 用户和程序看到的文件、目录、软连接及文件保护信息等都存储在其中。这种机制有利于用户和操作系统的交互。</font>

<font style="color:rgb(0, 0, 0);">尽管内核是 Linux 的核心，但文件却是用户与操作系统交互所采用的主要工具。这对 Linux 来说尤其如此，这是因为在 UNIX 传统中，它使用文件 I/O 机制管理硬件设备和数据文件</font>

### <font style="color:rgb(0, 0, 0);">虚拟文件系统、根文件系统和文件系统</font>
### <font style="color:rgb(0, 0, 0);">VFS</font>
<font style="color:rgb(0, 0, 0);">Linux支持多种文件系统类型，因为它将底层与应用层分隔开；而提供统一的接口支持应用层对于不同实现的文件系统的访问，这个统一的接口称为虚拟文件系统VFS。</font>

<font style="color:rgb(0, 0, 0);">kernel中以VFS去支持各种文件系统，如yaffs，ext3，cramfs等等。yaffs/yaffs2是专为嵌入式系统使用NAND型闪存而设计的一种日志型文件系统。在内核中以VFS来屏蔽各种文件系统的接口不同，以VFS向kernel提供一个统一的接口。</font>

### <font style="color:rgb(0, 0, 0);">根文件系统</font>
<font style="color:rgb(0, 0, 0);">文件系统指文件存在的物理空间，linux系统中每个分区都是一个文件系统，都有自己的目录层次结构。以“/”为顶级目录的文件系统称为根文件系统。</font>

<font style="color:rgb(0, 0, 0);">Linux启动时，第一个必须挂载的是根文件系统；若系统不能从指定设备上挂载根文件系统，则系统会出错而退出启动。系统正常挂载根文件系统之后可以自动或手动挂载其他的文件系统（根文件系统是其他文件的最终挂载点）。因此，一个系统中可以同时存在不同的文件系统。</font>

<font style="color:rgb(0, 0, 0);">也就是说：</font>

+ <font style="color:rgb(0, 0, 0);">根文件系统可以是任何kernel支持的文件系统类型(ext4,yaffs等)。但它必须包含linux内核启动时所必需的文件(根文件系统必需存在的目录 /dev /bin /sbin 等等)，不然系统启动会失败。</font>
+ <font style="color:rgb(0, 0, 0);">根文件系统是之所以有个根(/)字,是因为它是linux系统启动时挂载(mount,所谓挂载：就是在内存中创建一个虚拟的文件对应具体的存储空间分区的过程,挂载时不会保存信息,下次启动时得重新挂载)的第一个文件系统,启动完成后可以自动(配置etc/fstab)或者手动的方式将其它文件系统(分区)挂载到根文件系统中。</font>

### <font style="color:rgb(0, 0, 0);">其他文件系统</font>
<font style="color:rgb(0, 0, 0);">不同的文件系统类型有不同的特点，因而根据存储设备的硬件特性、系统需求等有不同的应用场合。在嵌入式Linux应用中，主要的存储设备为 RAM(DRAM, SDRAM)和ROM(常采用FLASH存储器)，常用的基于存储设备的文件系统类型包括：jffs2, yaffs, cramfs, romfs, ramdisk,initramfs, ramfs/tmpfs,ubifs等。</font>

### <font style="color:rgb(0, 0, 0);">uboot与根文件系统的关系</font>
<font style="color:rgb(0, 0, 0);">早期的uboot没有分区的概念，uboot只知道应该将什么数据烧写到存储介质的什么区间中。</font>

<font style="color:rgb(0, 0, 0);">（也就是说，对于uboot来看，只有起始地址结束地址等，A～B地址放内核，C～D地址放文件系统，即：规定哪个地址区间放内核或者文件系统等）</font>

<font style="color:rgb(0, 0, 0);">虽然此后，uboot中渐渐也有了MTD等管理分区部分的功能。尽管如此，不影响我们的学习理解。</font>

## <font style="color:rgb(0, 0, 0);">总结：</font>
_<font style="color:rgb(0, 0, 0);">（以下是本人【Schips】的理解）</font>_

<font style="color:rgb(0, 0, 0);">cpu首先执行位于0地址的uboot，uboot启动以后初始化一些资源，告诉内核有关的参数并引导内核，内核通过事先添加对于某种文件系统类型的支持驱动（相当于一小段程序），读取uboot等boot loader在指定的区域烧写制作好的文件系统镜像，内核解析并挂载成根文件系统，并在此基础上，通过VFS再挂载不同的文件系统类型，完成启动以后，再去管理有关的资源（包括应用程序）</font>
