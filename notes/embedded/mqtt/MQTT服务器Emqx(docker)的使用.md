## 普通部署
```shell
docker pull emqx/emqx:5.8.5
docker run -d --name emqx -p 1883:1883 -p 8083:8083 -p 8084:8084 -p 8883:8883 -p 18083:18083 emqx/emqx:5.8.5
```

# <font style="color:rgb(60, 60, 67);">二、Emqx 功能使用</font>
## 1、共享订阅


EMQX 的共享订阅机制是一种用于实现多个订阅者之间负载均衡的订阅模式。它的主要作用**是通过将消息分发给一组订阅者中的某个成员**，而**不是让所有订阅者都接收到相同的消息，从而提高消息处理的效率和系统的可扩展性**。这种机制特别适用于需要分布式处理或高吞吐量消息传递的场景，例如物联网（IoT）应用。

具体来说，EMQX 的共享订阅机制有以下作用：

1. **负载均衡**  
在共享订阅中，多个订阅者可以组成一个订阅组（通过 `$share/<group-name>/` 前缀定义），当消息发布到某个主题时，EMQX 会将消息分发给该组中的某一个订阅者，而不是广播给所有订阅者。这样可以避免重复处理消息，减轻单个订阅者的负担，实现负载的均衡分配。
2. **提高系统效率**  
通过限制每条消息只被组内的一个订阅者接收，共享订阅减少了消息的冗余传递，从而降低了网络带宽和计算资源的消耗。这在订阅者数量多或消息量大的情况下尤为重要。
3. **支持分布式架构**  
在分布式系统中，共享订阅允许将消息处理任务分散到多个节点或客户端。例如，在 EMQX 集群中，订阅者可以分布在不同的节点上，共享订阅机制确保消息能够合理分配，提升系统的整体处理能力。
4. **灵活的分组管理**  
EMQX 支持两种共享订阅前缀：`$share/<group-name>/`（带组名的共享订阅）和 `$queue/`（不带组名的共享订阅）。通过带组名的前缀，可以将订阅者分成不同的组，每个组独立接收消息，而组内实现负载均衡。这种灵活性使得系统设计者可以根据业务需求组织订阅者。
5. **适应高并发场景**  
在高并发或大规模连接的场景下（如智能交通、工业自动化），单个订阅者可能无法及时处理所有消息。共享订阅通过将消息分担给多个订阅者，确保消息处理的及时性，避免消息积压。

### 工作原理示例
假设有订阅者 s1、s2、s3 属于组 g1，订阅主题为 `$share/g1/t1`，订阅者 s4、s5 属于组 g2，订阅主题为 `$share/g2/t1`。当发布者向主题 `t1` 发送消息 `msg1` 时：

+ EMQX 会将 `msg1` 同时发送给 g1 和 g2 两个组。
+ 在 g1 组内，只有 s1、s2、s3 中的一个（例如 s2）会收到 `msg1`。
+ 在 g2 组内，只有 s4、s5 中的一个（例如 s5）会收到 `msg1`。

这种机制确保每个组都收到消息，但组内订阅者之间实现负载均衡。



### 类消费队列模式机制
在 EMQX 的共享订阅机制中，g1 组内只有 s1、s2、s3 中的一个（例如 s2）会收到 `msg1`，这是因为共享订阅的设计目标是实现负载均衡，而非广播。以下是具体原因和机制的解释：

### 1. **共享订阅的核心设计：负载均衡**
共享订阅（通过 `$share/<group-name>/` 前缀定义）旨在将消息分担给订阅组内的一个订阅者，而不是让组内的所有订阅者都收到相同的消息。这种设计避免了重复处理同一个消息的情况，从而提高效率并减少资源浪费。在你的例子中，g1 组内的 s1、s2、s3 被视为一个协作的订阅者集合，共同负责处理主题 `t1` 的消息。

当消息 `msg1` 被发布到主题 `t1` 时，EMQX 的共享订阅机制会从 g1 组中选择一个活跃的订阅者（例如 s2）来接收和处理这条消息，而不是将消息广播给 s1、s2、s3 全部。

### 2. **消息分发的调度策略**
EMQX 在实现共享订阅时，使用了一种调度策略来决定将消息发送给组内的哪个订阅者。通常，这种策略是基于以下几种可能的方式之一（具体实现可能取决于 EMQX 的配置和版本）：

+ **随机分发**：从当前在线的订阅者中随机选择一个（如 s2）。
+ **轮询（Round-Robin）**：按顺序依次分配给组内订阅者。例如，第一条消息给 s1，第二条给 s2，第三条给 s3，然后循环。
+ **基于负载或会话状态**：根据订阅者的连接状态、负载情况或 QoS（服务质量）级别选择一个最合适的订阅者。

在你的例子中，假设 s2 被选中，可能是因为它是当前轮询到的订阅者，或者随机选择的，或者它的连接状态最佳。无论具体策略如何，结果是只有 s2 收到 `msg1`，而 s1 和 s3 不会收到。

### 3. **与普通订阅的区别**
在普通的 MQTT 订阅中（不带 `$share` 前缀），如果 s1、s2、s3 都订阅了主题 `t1`，那么当 `msg1` 发布到 `t1` 时，三个订阅者都会收到这条消息。而共享订阅通过 `$share/g1/t1` 的形式明确告诉 EMQX：g1 组内的订阅者是协作关系，每条消息只需由组内的一个成员处理。这种行为类似于消息队列的消费模式，而不是发布-订阅的广播模式。

### 4. **为什么不全发？**
如果 g1 组内的 s1、s2、s3 都收到 `msg1`，会导致以下问题：

+ **重复处理**：多个订阅者处理同一条消息，浪费计算资源。
+ **逻辑冲突**：在某些业务场景中，消息可能只应被处理一次（例如订单分配），重复处理会破坏业务逻辑。
+ **性能下降**：随着订阅者数量增加，广播消息会显著增加网络和服务器的负载。

共享订阅通过限制每条消息只分发给一个订阅者，解决了这些问题。

### 5. **实际例子中的分发**
在你的场景中：

+ 主题 `t1` 收到消息 `msg1`。
+ g1 组的订阅主题是 `$share/g1/t1`，表示 s1、s2、s3 共享处理 `t1` 的消息。
+ EMQX 根据调度策略（例如轮询或随机）选择 s2，将 `msg1` 发送给它。
+ s1 和 s3 不会收到 `msg1`，但如果后续有新的消息（例如 `msg2`），可能会被分发给 s1 或 s3 中的一个。

### 总结
g1 组内只有 s2 收到 `msg1`，是因为 EMQX 的共享订阅机制通过负载均衡的设计，确保每条消息只被组内的一个订阅者接收。这种行为由调度策略控制，目的是优化资源利用、避免重复处理并支持分布式协作。
