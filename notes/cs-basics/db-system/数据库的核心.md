数据库核心知识可以分成几个层次来理解：**数据模型 → 关系理论 → SQL → 事务与并发 → 索引与存储 → 设计与范式 → 分布式与扩展**。下面按这个脉络讲解。

---

## 一、数据库是什么、解决什么问题

数据库是**有组织地存储、管理、查询数据**的系统。相比文件系统，它解决：

- **持久化**：数据不因程序退出而丢失
- **结构化查询**：用声明式语言（SQL）描述"要什么"，而非"怎么做"
- **并发控制**：多用户同时读写不破坏数据
- **事务与恢复**：崩溃后数据仍一致
- **约束与完整性**：主键、外键、唯一性等保证数据合法

DBMS（数据库管理系统）是管理数据库的软件，如 MySQL、PostgreSQL、Oracle、SQL Server；数据库是其中存放的数据集合。

---

## 二、数据模型：关系模型是核心

**关系模型**（Codd, 1970）用二维表表示数据：

- **关系（Relation）** = 表
- **元组（Tuple）** = 行
- **属性（Attribute）** = 列
- **域（Domain）** = 列的取值范围
- **键**：
  - **超键**：能唯一标识一行的属性集
  - **候选键**：最小超键
  - **主键**：选定的候选键
  - **外键**：引用另一表主键，维护参照完整性

其他模型：层次模型、网状模型、文档模型（MongoDB）、键值模型（Redis）、图模型（Neo4j）。关系模型因**数学基础严谨 + SQL 生态**成为主流。

---

## 三、关系代数与 SQL

关系代数是一组操作，SQL 是其工程化实现：

| 关系代数    | SQL 对应              |
| ----------- | --------------------- |
| 选择 σ      | `WHERE`               |
| 投影 π      | `SELECT` 列           |
| 笛卡尔积 ×  | `CROSS JOIN`          |
| 连接 ⋈      | `JOIN`                |
| 并 ∪ / 差 − | `UNION` / `EXCEPT`    |
| 聚集        | `GROUP BY` + 聚合函数 |

**SQL 分类**：

- **DDL**：`CREATE/ALTER/DROP`（定义结构）
- **DML**：`INSERT/UPDATE/DELETE`（操作数据）
- **DQL**：`SELECT`（查询）
- **DCL**：`GRANT/REVOKE`（权限）
- **TCL**：`COMMIT/ROLLBACK`（事务）

**查询执行逻辑顺序**（写 SQL 时很重要）：

```
FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
```

理解这个顺序能解释很多"为什么 SELECT 别名不能在 WHERE 用""HAVING 和 WHERE 区别"之类的问题。

**连接类型**：INNER JOIN（交集）、LEFT/RIGHT JOIN（保留一侧）、FULL OUTER JOIN、CROSS JOIN、自连接。

---

## 四、事务：ACID 与隔离级别

**事务**是一组要么全成功、要么全失败的操作。**ACID**：

- **A 原子性**：不可分割，失败全部回滚（靠 undo log）
- **C 一致性**：事务前后满足约束（由应用 + 数据库共同保证）
- **I 隔离性**：并发事务互不干扰（靠锁 / MVCC）
- **D 持久性**：提交后永久保存（靠 redo log / WAL）

**并发异常**：

- **脏读**：读到未提交数据
- **不可重复读**：同一事务内两次读同一行结果不同
- **幻读**：同一事务内两次范围查询行数不同
- **丢失更新**：两个事务覆盖彼此修改

**隔离级别**（SQL 标准）：

| 级别             | 脏读 | 不可重复读 | 幻读                                  |
| ---------------- | ---- | ---------- | ------------------------------------- |
| READ UNCOMMITTED | 可能 | 可能       | 可能                                  |
| READ COMMITTED   | 否   | 可能       | 可能                                  |
| REPEATABLE READ  | 否   | 否         | 可能（MySQL InnoDB 用间隙锁基本避免） |
| SERIALIZABLE     | 否   | 否         | 否                                    |

**实现机制**：

- **锁**：共享锁/排他锁、行锁/表锁、意向锁；两阶段锁协议
- **MVCC**：多版本并发控制，读不加锁，靠版本链 + Read View 实现快照读（MySQL InnoDB、PostgreSQL 都用）
- **WAL（预写日志）**：先写日志再写数据，保证崩溃恢复

## 五、索引与存储

**索引**是加速查询的数据结构，代价是写入变慢、占空间。

- **B+ 树索引**（最常用）：矮胖树，范围查询和等值查询都好，叶子节点链表连接
- **哈希索引**：仅等值查询，O(1)
- **全文索引**：倒排索引
- **聚簇索引 vs 非聚簇索引**：InnoDB 主键即聚簇索引，数据存叶子节点；二级索引叶子存主键值，需**回表**
- **覆盖索引**：查询列都在索引中，避免回表
- **最左前缀原则**：联合索引 (a,b,c) 能用于 a、a+b、a+b+c 的查询

**存储引擎**（以 MySQL 为例）：

- **InnoDB**：支持事务、行锁、外键、MVCC、崩溃恢复，默认引擎
- **MyISAM**：表锁、不支持事务，已较少用

**存储结构**：页（page，通常 16KB）为最小 I/O 单位；缓冲池（Buffer Pool）缓存页；日志包括 redo log（重做，保证持久性）、undo log（回滚，保证原子性）、binlog（MySQL 服务层，用于复制和恢复）。

## 六、数据库设计：范式与反范式

**范式**（减少冗余、避免更新异常）：

- **1NF**：列不可再分
- **2NF**：非主属性完全依赖候选键（消除部分依赖）
- **3NF**：非主属性不传递依赖候选键
- **BCNF**：每个决定因素都是候选键

**反范式**：为查询性能适度冗余（如冗余计数、宽表），用空间换时间。

**设计步骤**：需求分析 → 概念设计（ER 图）→ 逻辑设计（关系模式 + 范式化）→ 物理设计（索引、分区、存储）。

**ER 图**：实体、属性、联系（1:1、1:N、M:N），M:N 需拆成关联表。

## 七、查询优化

- **执行计划**：`EXPLAIN` 看访问方式（全表扫描 / 索引扫描）、连接顺序、是否用临时表/文件排序
- **优化手段**：建合适索引、避免 `SELECT *`、避免在索引列上做函数运算、用覆盖索引、小表驱动大表、避免隐式类型转换、分页优化（延迟关联 / 游标）
- **代价模型**：基于统计信息（行数、基数、选择率）估算代价，CBO（基于代价优化）选择计划

---

## 八、分布式与扩展

- **垂直扩展**：加 CPU/内存/磁盘
- **水平扩展**：分库分表（Sharding）、读写分离（主从复制）
- **复制**：主从异步/半同步复制，binlog 同步
- **CAP 定理**：一致性、可用性、分区容忍性三者不可兼得；分布式数据库通常在 C 与 A 间取舍
- **BASE**：基本可用、软状态、最终一致
- **NewSQL**：TiDB、CockroachDB 等兼顾分布式与事务
- **NoSQL**：键值（Redis）、文档（MongoDB）、列族（HBase）、图（Neo4j），按场景选型
